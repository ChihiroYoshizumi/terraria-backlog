# Achievement Registry

攻略課題の有無に関係なく達成事実を Backlog に保存し、後付け Mapping と再同期の根拠にする。

## 背景・目的と利用シナリオ

攻略担当者として、目標課題を作る前に達成した内容も後から利用したい。達成記録は課題やアイテムの現在状態から独立して保持する。

上位仕様：第4節、第5.1〜5.2節、第9節。状態：draft。

## 対象・対象外

対象は達成キー、保存項目、保存確認、冪等性。独自 DB、永続 Outbox、生イベント履歴、達成の取り消し、正確な過去日時の復元は対象外とする。

## 機能要件・正常時の振る舞い

1. PHP が観測を評価し、`(world_key, achievement_key)` を確定する。
2. Backlog の Registry 区分を検索し、両キーを完全一致で確認する。
3. 既存の有効な達成記録があれば利用する。なければ作成して保存を確認する。
4. 保存確認の結果を納品処理・課題同期に返す。

| 論理項目 | 意味 |
| --- | --- |
| Registry ID | Backlog の課題 ID / キー |
| World Key・Achievement Key | 達成の論理識別子 |
| Achievement Type | boss / world / event / item |
| 件名・状態 | 達成名と設定した達成済み状態 |
| メタデータ | 検知元、観測日時、必要なアイテム・チェスト情報 |
| 登録日時 | Backlog に保存した日時。実際の達成日時とは区別 |

キーをカスタム属性に保持する。専用プロジェクトまたは課題種別で攻略課題と区別する。検索は全ページを考慮し、検索失敗を未登録として扱わない。

## 例外・境界条件

| 状況 | 期待する扱い |
| --- | --- |
| 同じ観測を繰り返す | 新しい達成を作らず既存記録を使用 |
| 作成応答がタイムアウト | 保存未確認として再検索。無条件に再作成しない |
| 同じ論理キーの物理重複 | 重複を検出し、1つの論理的な達成として扱う |
| アイテム取り出し・Mapping 解除 | 達成を維持 |
| Registry の削除・改変 | 再取得できる現在状態だけが補完の根拠 |
| 再判定で過去日時が不明 | 実際の達成日時として登録日時を流用しない |

書き込みは単一の論理ライターに集約する。厳密な exactly-once は保証しない。API Key を Registry に保存しない。

## 関連機能との責務分担

[Collection Chest](collection-chest.md)と[World Progress](world-progress.md)が判定対象を供給する。成功 ACK の表示は納品側、攻略課題の更新は[Backlog 同期](backlog-sync.md)が担当する。

## 成功基準・受け入れ条件

- AC-02：アプリ専用 DB なしで、再起動後も保存済み達成を利用できる。
- AC-11：通常の重複通知・定期照合で Registry が増殖しない。
- AC-12：作成応答を失った場合、既存登録を再検索して確認できる。
- AC-12：物理重複を二重達成として扱わない。
- AC-03・05との連携：課題なしでも保存でき、取り出し後も記録が残る。

## 未決事項・詳細設計への引き継ぎ

- プロジェクト分離、属性型・ID・契約上の利用可否、完了状態の設定。
- 検索の比較仕様、ページ分割、結果不明時の確認手順。
- 単一ライターの実行方式と、物理重複を見つけた際の運用手順。
