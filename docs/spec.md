# Terraria × Backlog ワールド進捗管理システム仕様

Terraria のマルチプレイワールドで達成した攻略・収集進捗を Backlog に記録し、攻略課題を自動で完了にする。PHP を主実装とし、アプリケーション専用 DB を持たず、Backlog に達成記録と課題との対応を永続化する。

本書はシステム全体の最上位仕様である。後続の設計・タスク分割・実装は本書に従う。過去の検討にあった SQLite 構成と、一過性イベントの無損失保証は採用しない。

## 1. 目的と利用者

管理するのは「このワールドで何を達成したか」であり、プレイヤー個人の実績ではない。参加者は普段どおり遊び、収集品を共有の納品箱へ入れる。攻略担当者は Backlog で目標を整理し、達成後に作った課題も既存の記録に紐付けられる。

- プレイヤー：Vanilla Terraria クライアントで参加し、収集品を納品する。
- 攻略担当者：Backlog の攻略課題と Mapping を管理する。
- サーバー管理者：TShock、Adapter、PHP Bridge、認証情報、再同期を管理する。

## 2. スコープ

| 対象 | MVP の要件 |
| --- | --- |
| マルチプレイ | TShock 専用サーバーを使用し、クライアントに MOD を要求しない |
| Boss / World State | 現在のワールド状態から再判定できる撃破・進行フラグを記録する |
| Collection Chest | `BACKLOG_COLLECTION` に現存するアイテムを取得済みとして記録する |
| Achievement Registry | 攻略課題の有無に関係なく達成事実を Backlog に保存する |
| Mapping | Achievement と攻略課題の対応を Backlog に保存する |
| 課題同期 | 事前・後付けの Mapping に対応し、達成済みの課題を完了にする |
| 再同期 | 起動時・定期・管理者の手動操作で、再取得可能な状態を照合する |
| 運用 | 起動手順またはスクリプト、設定方法、障害時の確認方法を提供する |

## 3. 非スコープ

- Steam 実績・アカウント連携、プレイヤー個人の進捗、Inventory の監視。
- Collection Chest への納品がないアイテムの取得推測、取得経路の証明。
- 建物・部屋の自動認識、展示家具や看板を利用した収集判定。
- Backlog からの Terraria ワールド変更、アイテム付与・消費。
- Vanilla の Host & Play、純正専用サーバーのみの構成、tModLoader 対応。
- AI による攻略課題の自動生成、複数 Achievement の AND / OR 条件。
- 数量の累積納品、撃破回数、達成の取り消し、正確な過去の達成日時の復元。
- Terraria 側に再判定可能な状態が残らず、Registry 保存にも失敗した一過性イベントの復元。
- 上記イベントを救済する SQLite、ファイルキュー、永続 Outbox、独自のイベント履歴ストア。

## 4. アーキテクチャと技術方針

```text
Vanilla Terraria Clients
          |
          v
TShock Dedicated Server
  World State / Collection Chest
          |
          v
Thin C# Adapter
          | 状態・イベント通知（HTTP、信頼境界を越える場合は HTTPS）
          v
PHP Terraria Backlog Bridge
  Achievement 判定 / Registry 照合 / Mapping / 再同期
          | Backlog API（HTTPS）
          v
Backlog
  Achievement Registry       攻略課題（Mapping を保持）
```

| 構成要素 | 責務 |
| --- | --- |
| TShock | ゲームサーバーとワールドの通常の保存・復元 |
| C# / .NET Adapter | サーバーイベント検知、安全なタイミングでの状態取得、PHP への転送、PHP の結果をゲーム内へ表示 |
| PHP Bridge | Achievement Key の解釈、達成判定、入力検証、Backlog API 操作、冪等性、後付け Mapping、再同期 |
| Backlog Registry | ワールド単位の達成事実の永続ストレージ |
| Backlog 攻略課題 | 利用者向け UI と Mapping の永続ストレージ |

PHP を主実装言語とする。Laravel は候補とし、採用・バージョンは詳細設計で決定する。C# に達成ルール、Mapping 判定、Backlog API クライアントを実装しない。

「DB なし」は Bridge と独自 Adapter が進捗・Mapping 用 DB を追加しないことを意味する。TShock 自身の内部ストレージや Terraria のワールドファイルは対象外である。設定ファイル・ログ・消失可能なメモリキャッシュは使用できるが、復旧の唯一の根拠にしない。Laravel を採用する場合も DB 依存のキュー・セッション等を必須にしない。

## 5. 識別子と論理データモデル

### 5.1 ワールドと Achievement

達成の論理識別子は `(world_key, achievement_key)` とする。同じキーでもワールドが異なれば独立した達成である。

`world_key` は再起動・表示名変更で変わらない値を使用する。採用バージョンで利用できるワールド固有 ID を確認し、利用できない場合は管理者設定の固定 ID を使用する。ワールド名だけで識別しない。別ワールドとして扱うコピーには別キーを割り当てる。

| 種別 | Key の形式・例 | 意味 |
| --- | --- | --- |
| Boss | `boss:eye_of_cthulhu`、`boss:moon_lord` | 対応する永続的なワールド状態で確認できる撃破 |
| World | `world:hardmode` | Hardmode への移行 |
| Event | `event:<identifier>` | 永続フラグで再判定できるイベントの達成のみ |
| Item | `item:<item-id>` | Collection Chest で 1 個以上確認したアイテム種別 |

Item は有効な Terraria Item ID 全般を記録可能とし、攻略課題があるアイテムだけに限定しない。Prefix や個数ごとの別実績は作らない。

Boss の初期候補は Eye of Cthulhu、Skeletron、Wall of Flesh、The Destroyer、The Twins、Skeletron Prime、Plantera、Golem、Lunatic Cultist、Moon Lord とする。各候補は詳細設計で永続フラグとの対応を確認する。共有フラグから個別撃破を区別できない場合や永続フラグがない場合は、個別撃破を推測して登録しない。対応表と対象外の理由を明示し、代替イベントの無損失保存は追加しない。

### 5.2 Achievement Registry

Backlog の専用プロジェクト、または専用課題種別で Registry を攻略課題から区別する。`TERRAREG` と `TERRA` は構成例であり、実際のプロジェクトは設定で指定する。

| 論理項目 | 保存内容 |
| --- | --- |
| Registry ID | Backlog 課題 ID / 課題キー |
| Terraria World Key | `world_key`。必須 |
| Terraria Key | `achievement_key`。必須 |
| Achievement Type | boss / world / event / item |
| 件名 | 人間向けの達成名 |
| 状態 | 設定した達成済み状態 |
| メタデータ | 検知元、観測日時、必要に応じて Item ID・チェスト情報 |
| 登録日時 | Backlog への保存日時 |

キーはカスタム属性で保持する方針とする。属性の利用可否・型・ID・契約プランは導入時に確認する。Registry の登録日時を実際の撃破・入手日時とは扱わない。再判定で実際の日時が不明なら、その旨を記録する。

Registry は達成事実の正本となる。登録後にアイテムを取り出す、Mapping を削除する、攻略課題を削除する操作では、達成記録を取り消さない。

### 5.3 Mapping

攻略課題の `Terraria World Key` と `Terraria Key` カスタム属性を Mapping とする。別の Mapping テーブルは作成しない。

- 1 課題は 1 ワールドの 1 Achievement に対応する。
- 同じ Achievement を複数の攻略課題へ紐付けてよい。
- Registry に未登録の Achievement も事前に紐付けられる。
- 属性の削除は Mapping の解除であり、Registry の削除ではない。
- 不正なキー、欠けた属性、対象外プロジェクトには更新を行わず、診断可能なエラーを残す。

検索結果は PHP 側で両キーの完全一致を確認する。Backlog API の文字列検索を一意制約とみなさず、ページ分割も考慮する。カスタム属性検索の具体的な比較仕様は詳細設計で確認する。

## 6. Collection Chest

ワールド内で名前が `BACKLOG_COLLECTION` に一致するチェストを納品箱とする。名前は設定可能とし、複数存在する場合はすべて対象にする。座標は観測情報であり、恒久的な識別条件にしない。

1. Adapter がチェスト変更を検知する。
2. サーバー側で変更が反映された後、チェスト内容を再取得する。
3. PHP が有効な Item ID と正の個数から達成を判定する。
4. Mapping の有無に関係なく Registry の保存、または既存登録を確認する。
5. Adapter がゲーム内に登録成功の ACK を表示する。
6. 対応する攻略課題があれば完了に同期する。

イベントの差分だけで「追加された」と判定しない。通常ドラッグ、Shift 操作、Quick Stack、複数スロット更新を経ても、現在内容の再取得で同じ結果に収束させる。イベントを集約してよいが、定期スキャンを省略しない。

ACK は Registry への永続化確認を意味し、攻略課題の完了とは区別する。「登録しました。取り出して OK です」と表示した後は取り出せる。既に登録済みの場合もその旨を表示できる。

保存失敗・結果不明時は成功 ACK を返さず、「登録を確認できません。アイテムをチェストに残してください」と案内する。取り出しを物理的に禁止する機能は MVP の必須要件としない。ACK 前に取り出して記録が残らなかった場合は復旧保証の対象外となる。

チェストが改名・撤去された場合、過去の Registry は維持する。未登録のアイテムは対象チェストで再確認できるまで登録を保証しない。

## 7. Boss / World State reconciliation

イベント通知を早期検知に使い、現在のワールド状態との照合を復旧手段とする。

1. ワールド読み込み完了後、安定した `world_key` を確定する。
2. Adapter が Boss / World State と対象チェストの現在状態を取得する。
3. PHP が対象 Achievement を評価し、Registry の不足分を登録する。
4. Registry と Mapping を照合し、未反映の攻略課題を完了にする。

起動時・定期・手動再同期でこの処理を実行する。PHP のみが再起動した場合も、Adapter から新しい状態を再取得できること。定期間隔と手動操作の具体的なインターフェースは詳細設計で定める。

停止中の撃破でも、復帰後のワールド状態に証拠が残っていれば補完する。サーバークラッシュで未保存のワールド状態自体が失われた場合、失われた内容を推測しない。ワールドを巻き戻しても既存 Registry は自動で取り消さない。

## 8. Backlog 同期と後付け Mapping

同期方向は Terraria → Registry → 攻略課題の一方向とする。攻略課題の手動完了を Terraria の達成事実として逆輸入しない。

| 契機 | 結果 |
| --- | --- |
| 達成を検知し、Mapping がない | Registry のみ保存 |
| 達成を検知し、Mapping がある | Registry 保存確認後に対象課題を完了 |
| 達成前に Mapping を追加 | 課題状態は変更せず、以後の達成を待つ |
| 達成後に Mapping を追加 | 保存済み Registry を用いて対象課題を完了 |
| Mapping を解除 | 以後の同期対象から外す。Registry と課題状態は維持 |
| 対象課題が既に完了 | 不要な更新・コメントを追加しない |

Backlog 上の Mapping 追加・変更を定期照合で発見する。手動同期ではその実行時に再評価する。Backlog が正常な場合、次の正常な照合サイクルの完了までに反映する。Webhook の採用は任意であり、配送成功を復旧の前提にしない。

Mapping が有効で Registry が達成済みなら、手動で再オープンされた課題も次回同期で完了する。自動同期を止める場合は Mapping を解除する。Mapping を変更しても以前の完了状態は自動で戻さない。

完了状態 ID はプロジェクト設定から指定・検証する。表示名や固定の数値を前提にしない。

## 9. 冪等性と障害時の保証

同じ観測の繰り返しは同じ論理的な達成として扱う。通常の重複通知・定期照合・再起動で Registry を増殖させず、完了済み課題を繰り返し更新しない。

Backlog は独自 DB の一意制約やトランザクションの代替ではない。MVP は同一 Registry に対する書き込みを単一の論理ライターへ集約する。作成結果が不明なら再検索して確認し、無条件に再作成しない。API の応答喪失等で物理的な重複が生じた場合も、同一キーとして検出・照合し、二重の達成として扱わない。厳密な exactly-once は保証しない。

| 障害・状態 | 復旧時の動作と保証 |
| --- | --- |
| Backlog 停止中に Boss / World が進行 | 復旧後に取得できるフラグから Registry を補完 |
| Backlog 停止中に納品、アイテムが残存 | 復旧後のチェスト再スキャンで補完し ACK |
| Registry 保存済み、攻略課題の更新失敗 | Registry と Mapping の再照合で更新を再試行 |
| Registry 保存成功後、ACK が届かない | 再照合で既存登録を確認し ACK を再表示可能 |
| 保存要求がタイムアウト | 保存成否を再確認。未確認の間は成功 ACK を返さない |
| PHP / Adapter 再起動、キャッシュ消失 | Backlog と現在のワールド状態から再構成 |
| 保存前にアイテム撤去、再判定根拠も消失 | 復元を保証しない |
| Registry 自体が削除・改変された | 現在状態で確認できる分だけ再判定。失われた過去の事実は保証しない |

一時エラー・レート制限には待機を入れ、API 制約に従って再試行する。認証・権限・設定のエラーは管理者に診断情報を残す。API 検索失敗を「未登録」と解釈して作成しない。未確認の観測は次回スキャンで再取得し、永続的な送信待ちキューを導入しない。

Backlog 通信でゲームのメイン処理を待たせない。タイムアウトとメモリ上の待機量を制限し、混雑時は再スキャンで補完する。

## 10. セキュリティと運用

- Backlog API Key は PHP 側の環境変数またはアクセス制限した設定で管理する。Git、ログ、課題、ゲーム内チャット、クライアント、Adapter に配布しない。
- Backlog 通信は HTTPS とする。Adapter → PHP も信頼境界を越える場合は HTTPS を必須とし、認証と送信元・対象ワールドの許可を検証する。
- 外部から自由に達成を登録できる公開エンドポイントを作らない。偽造された通知、未認証の手動同期、対象外ワールドの通知を拒否する。
- 入力の型・サイズ・Item ID・キーを検証する。通知に含まれる任意 URL や任意プロジェクトへ書き込まない。
- Backlog の操作権限は対象プロジェクトに必要な範囲へ限定する。Registry の編集権限は運用上制限し、手動変更を通常の利用手順にしない。
- ゲーム内に管理コマンドを設ける場合、Mapping 変更・手動同期は管理者権限で保護する。Backlog での Mapping 編集は Backlog の権限に従う。
- ログにはワールドキー、処理種別、同期結果、エラー種別を記録する。秘密情報を含む URL・ヘッダーや不要なプレイヤー情報は残さない。
- 導入時に対応する Terraria / TShock / .NET / PHP の組み合わせ、必要属性、完了状態、同期間隔を検証する。設定不備を検出した場合は誤更新を止め、原因を表示する。

## 11. 受け入れ条件

| ID | 確認シナリオと期待結果 |
| --- | --- |
| AC-01 | MOD のない対応バージョンの Terraria クライアントが TShock に接続し、納品と進捗同期を利用できる |
| AC-02 | 専用 DB・永続キューなしで起動し、PHP / Adapter 再起動後も Backlog の Registry と Mapping が利用できる |
| AC-03 | 攻略課題がないアイテムを納品すると Registry に登録され、保存確認後に成功 ACK が表示される |
| AC-04 | 通常ドラッグ・Shift・Quick Stack の各操作で、最終的なチェスト内容から同じ達成を判定できる |
| AC-05 | 登録済みアイテムを取り出して再同期しても、Registry と完了済み課題が未達成に戻らない |
| AC-06 | Registry 登録後にアイテムを取り出し、PHP を再起動してから Mapping を追加しても、次の正常な照合で課題が完了する |
| AC-07 | 未達成の Mapping では課題を変更せず、達成と Registry 保存の後に完了する |
| AC-08 | Adapter 停止中の進行がワールドに保存されていれば、起動時に対象フラグから Registry を補完できる |
| AC-09 | Backlog 障害中は成功 ACK を出さず、残された納品アイテムを復旧後に登録できる |
| AC-10 | Registry 保存後に攻略課題更新だけを失敗させても、再同期で完了にできる |
| AC-11 | 重複通知・定期照合では Registry を重複作成せず、完了済み課題へ不要な更新をしない |
| AC-12 | 保存応答を失った場合に成功を断定せず、再検索で既存登録を確認できる。検出した物理重複は同一の論理達成として扱う |
| AC-13 | 同一 Achievement のある World A と未達成の World B を用意し、A の記録で B の課題が完了しない |
| AC-14 | 同じ Achievement の複数課題はすべて完了できる。不正・対象外の Mapping は更新しない |
| AC-15 | Mapping 解除後の課題は自動更新されず、Registry は残る |
| AC-16 | 未認証・対象外ワールドの通知を拒否し、ログとゲーム内表示に API Key が含まれない |
| AC-17 | 保存失敗後にアイテムと再判定根拠を失ったケースで、達成を推測して登録しない |
| AC-18 | Backlog 通信を遅延・停止させてもゲーム進行をブロックせず、復旧後に再照合が進む |

## 12. 詳細設計で確定する事項

本書の境界を維持したまま、次工程で以下を確定する。

- 対応バージョン、PHP フレームワーク、起動・配置方法。
- Boss / World / Event の永続フラグ対応表と、識別不能な達成の扱い。
- Adapter の状態取得タイミング、通知形式、認証方式、ACK の相関方法。
- Backlog のプロジェクト分離、属性 ID、検索・ページ分割、重複検出手順。
- 同期間隔、タイムアウト、再試行間隔、単一ライターの実行方式、手動操作方法。

## 13. 技術確認用の一次資料

- [Backlog API：課題一覧の取得](https://developer.nulab.com/ja/docs/backlog/api/2/get-issue-list/) — カスタム属性検索とページ分割の確認先。
- [TShock 公式ソース](https://github.com/Pryaxis/TShock) — 採用バージョンのイベントフックと状態取得方法の確認先。

資料上の API やフックの存在だけで、全 Achievement の再判定可能性を保証しない。採用バージョンで対応表と受け入れ条件を検証する。
